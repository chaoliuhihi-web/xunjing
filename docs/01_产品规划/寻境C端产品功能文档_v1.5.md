## 1. 产品决策摘要

星河寻境作为完整品牌，C 端产品统一使用“寻境”。寻境不以“泛 AI 文旅平台”作为入口，也不正面竞争携程的旅行预订、高德的地图导航、小红书的攻略社区或系统相册的照片管理。

### 1.1 品牌与产品命名

| 层级 | 统一名称 | 使用范围 |
| --- | --- | --- |
| 完整品牌 | 星河寻境 | 公司主体、正式合作、版权和品牌背书 |
| C 端产品 / App | 寻境 | 用户下载、使用和传播时看到的主产品名 |
| 应用商店名称 | 寻境旅行——行程、足迹与旅行书 | 解决“寻境”含义偏抽象的问题，也作为单名不可用时的上架方案 |
| 产品内助手 | 寻境旅伴 / 小境 | 攻略理解、路线核对、现场提醒和作品修改助手 |
| 行前产品能力 | 寻境行程 | 攻略链接导入、计划编辑、动态预演和同行查看 |
| 行后传播产品 | 寻境电影 | 计划电影和真实回忆电影 |
| 核心付费商品 | 寻境旅行书 | 电子书、印刷校样和实体旅行书 |

命名约束：

- 不把“旅伴”单独作为总产品名，避免被理解为找搭子、结伴社交或通用聊天机器人。
- 不再把“旅程本”作为 App 总名称，它只描述行后作品的一部分。
- “旅行书”保留为核心付费商品名称，不扩张为整个产品品牌。
- 对消费者的首屏、分享页和应用图标优先展示“寻境”；“星河寻境”放在品牌背书、关于我们和正式合同中。

寻境提供两个平行入口，最终汇入同一个真实旅程和作品体系。用户不需要先使用行前功能，才能在旅行结束后做书。

```text
入口 A：规划一次新旅行
  -> 导入攻略或从空白创建路线
  -> 动态播放计划行程并分享给同行查看
  -> 行中查看今日行程、调起导航并按需轻记录
  -> 行后一次选择原始照片并自动重建实际旅程

入口 B：旅行已经结束
  -> 直接选择原始照片和视频
  -> 系统依据时间、位置和视觉证据识别旅程
  -> 用户只核对少量高影响信息

两个入口共同进入：
  -> 生成真实路线、旅行故事、足迹卡和回忆电影
  -> 自动生成完整旅行书首版
  -> 用户真实翻阅、少量修改、付款并获得实体书
  -> 作品沉淀到个人与家庭旅行档案
```

核心原则：

1. 行前规划和动态预演负责获客、激活和同行查看，不设置投票或正式确认流程，也不作为主要收费点。
2. 行中以查看行程和调起导航为主；轨迹、打卡和共同记录都是可选增强，不能成为成书前提或转化漏斗门槛。
3. 行后寻境电影负责传播，寻境旅行书负责付费，个人旅行档案负责长期沉淀。
4. 所有阶段必须围绕同一趟旅行连续衔接，不再让路线、足迹、游记、电影和成书成为互不相通的功能孤岛。
5. 用户只选择一次原始照片；缩略图、预览图和印刷文件由系统内部派生，不向用户暴露分阶段素材处理流程。
6. 标准旅行书默认自动生成和自动质检，人工只处理例外，不逐单逐页核对。
7. 完整产品不等于复杂操作：系统能力可以丰富，用户在每个阶段只看到当前最相关的一个主动作。
8. 当前版本只规划 C 端与支撑其交付的运营后台；合作方、加盟、渠道分润和结算功能暂不进入产品范围。
9. 照片位置是可追溯证据，不是必然事实；优先使用系统相册原始资产的拍摄时间和位置，完整轨迹只作可选增强，缺失时明确降级而不编造经纬度。
10. 所有创作功能遵循“系统先给完整首版，用户再处理少量例外”；不让用户从空白画布、模板选择或逐页编辑开始。
11. 借鉴 Polarsteps 的“完整旅程回放”和 Journi 的“自动成书”只采用经过官方资料核验的产品机制，不复制品牌、图标、文案、视觉资产或受保护页面；所有路线表达继续遵守寻境自己的真实证据与中国地图合规要求。
12. 旅行书和出版物的正式生成后台在 Linux 服务器上运行 Codex Harness，必须加载经版本、哈希、测试、灰度和回滚管理的 `travel-memory-book` Skill；Skill 未加载时生成任务失败关闭，不以通用提示词或人工逐页制作暗中托底。

### 1.2 完整产品的六个闭环

寻境不是单一照片书工具，也不是把多个旅行功能拼成宫格。完整产品必须同时形成以下六个相互连接的消费者闭环：

| 闭环 | 用户结果 | 代表能力 |
| --- | --- | --- |
| 行前计划 | 快速获得能看懂、能分享的真实行程 | 攻略导入、路线编辑、动态预演、同行查看 |
| 行中陪伴 | 顺利出行并在不被打扰的情况下留下线索 | 今日行程、导航调起、记下这里、可选足迹和共同素材 |
| 行后重建 | 自动还原真正发生的旅行 | 照片时间与位置、计划与实际对齐、人物和事件识别 |
| 数字作品 | 得到可分享而不是半成品的内容 | 旅行故事、足迹卡、计划电影、回忆电影 |
| 实体收藏 | 得到可翻、可改、可印、可售后的旅行书 | 完整首版、真实翻页、自然语言修改、校样、付款和履约 |
| 长期档案 | 让多次旅行逐渐形成个人与家庭记忆资产 | 作品库、家庭旅行档案、城市足迹和年度回顾 |

六个闭环都属于完整产品，但不要求一次性以最高复杂度上线。首期必须让每个闭环至少有一条真实可用路径，再依据真实用户行为增强深度。

## 2. 目标用户与首发场景

### 2.1 首批核心用户

首批聚焦以下人群：

- 28–45 岁家庭旅行决策者。
- 一次家庭、亲子或三代同游会拍摄 100 张以上照片。
- 有整理照片、记录孩子成长、赠送家人或制作实体纪念物的动机。
- 愿意从攻略导入开始规划，或者在旅行结束后直接一次选择照片；愿意翻阅首版并确认印刷。

### 2.2 场景优先级

| 优先级 | 场景 | 付费动机 |
| --- | --- | --- |
| P0 | 亲子家庭旅行 | 孩子成长、家庭共同记忆、易加印赠送 |
| P0 | 三代同游、给父母做旅行书 | 子女付费、礼物属性强 |
| P1 | 情侣、蜜月、纪念日旅行 | 仪式感、礼赠和分享 |
| P1 | 毕业旅行 | 群体纪念、多人加印 |
| P2 | 一般 Citywalk、个人足迹 | 分享价值高，但实体书付费动机偏弱 |

### 2.3 非目标用户

首期不服务以下主需求：

- 只想比价、订机票或酒店的用户。
- 需要专业户外轨迹、救援或高精度运动数据的用户。
- 只想使用复杂视频时间轴或专业剪辑软件的用户。
- 只想管理全部人生照片和家庭云相册的用户。

## 3. 产品价值与输出层级

### 3.1 用户价值

用户不是购买“AI 功能”，而是完成一件自己很难完成的事：

- 把零散攻略变成可执行路线。
- 把抽象路线变成可播放、可讨论的计划。
- 在不打断旅行的前提下，把过程变成有时间、地点和人物关系的真实记录。
- 把大量照片、视频以及可选足迹变成一部完整作品。
- 把数字作品变成可收藏、可赠送的实体旅行书。

### 3.2 四层输出

| 阶段 | 免费输出 | 主要作用 | 是否核心收费 |
| --- | --- | --- | --- |
| 行前 | 每日路线卡、15–30 秒计划行程预演 | 检查路线、同行查看、分享获客 | 否 |
| 行中 | 今日行程、导航入口、可选完整足迹或“记下此刻” | 帮用户顺利出行，不增加记录负担 | 否 |
| 行后 | 30–90 秒旅行电影、足迹海报、旅行故事 | 分享传播、召回用户 | 否 |
| 成书 | 完整电子书、印刷校样、实体旅行书 | 收藏、礼赠、付费交付 | 是 |

### 3.3 产品口号

对消费者统一使用主口号：

> 寻境——把攻略变成旅程，把旅程变成电影和一本书。

在产品流程说明和较长传播物料中可使用辅助口号：

> 一趟旅行，从路线预演，到真实足迹，再到一部电影、一本书。


### 3.4 最低操作原则

寻境根据用户所处阶段提供两条低操作路径。

行前开始的用户只需要：

1. 粘贴攻略链接、正文或截图，保存系统生成的行程。
2. 按需播放预演并分享给同行；旅行中只在需要时查看下一站或调起导航。
3. 行后一次选择这趟旅行的原始照片和视频，等待系统生成完整作品。
4. 翻阅旅行书首版，仅在必要处修改，确认后付款印刷。

行后直接进入的用户只需要：

1. 选择一组旅行照片和视频。
2. 核对日期、目的地和人物等不超过 3 个高影响问题。
3. 等待系统生成实际路线、回忆电影和旅行书首版。
4. 翻阅首版，仅在必要处修改，确认后付款印刷。

所有其他动作都是可选增强：同行加入、完整足迹、“记下这里”、语音备注、人物关系补充、自然语言改单和人工精修。系统不得通过连续弹窗、红点或任务清单把这些可选动作伪装成必做流程。

### 3.5 厚度与落地约束

每项进入当前范围的功能必须同时满足四个条件：

1. 有真实输入，不依赖硬编码样例或演示数据。
2. 有用户可消费的完整输出，不把内部草稿当作成品。
3. 有失败、弱网、权限拒绝和数据不足时的明确回退。
4. 有可重复执行的用户验收和服务端证据。

因此首期采用“成熟能力组合”而不是重复建设基础设施：导航调起合规地图应用；完整轨迹保持可选；无轨迹时用照片和计划重建旅程；电影使用自动成片模板；旅行书使用固定印刷规格与受控版式；运营后台处理少量例外。产品厚度来自六个闭环的真实衔接，不来自大量未完成的按钮。

## 5. C 端信息架构

### 5.1 一级导航

建议使用三个一级入口：

1. `旅程`：即将出发、旅行中和历史旅程。
2. `作品`：电影、足迹卡、故事和旅行书。
3. `我的`：订单、成员、隐私、授权、地址和售后。

不设置独立的“记录”一级入口。完整足迹、“记下这里”和共同记录入口只在正在进行的旅程内按需出现。

首页不展示功能宫格。首次进入时只提供两个清晰入口，进入旅程后再按状态突出一个主动作：

- 首次进入：`规划一次新旅行` / `旅行结束了，做成作品`。
- 选择规划：导入一份攻略或从空白创建。
- 选择行后：直接选择照片并识别旅程。
- 已有计划：播放并确认路线。
- 旅行中：查看下一站 / 导航。
- 已结束：生成这次旅行的首版作品。
- 已有首版：翻阅和修改旅行书。

### 5.2 寻境旅伴

“寻境旅伴”是产品内的情境助手，用户可以称它为“小境”。它不占据首页主入口，也不把寻境变成聊天机器人产品。

小境只在当前旅程上下文中提供帮助：

- 行前解释攻略解析结果、提示同名地点和明显绕路。
- 行前帮助同行快速看懂路线；加入旅程后提示共同记录入口和素材归属。
- 行中按需回答下一站、路线和记录状态，不主动催促打卡或补资料。
- 行后只对影响叙事或印刷的少量高影响不确定项请求核对。
- 用户修改电影或旅行书时，把自然语言要求转成可确认的修改范围。

小境不得替用户编造真实到访、自动公开轨迹、擅自确认印刷或扩张为泛旅行问答入口。

## 6. 寻境行程（行前功能）

### 6.1 创建旅程

支持：

- 输入目的地、日期、同行人和旅行主题。
- 从空白开始。
- 从地点清单开始。
- 复制并粘贴第三方平台攻略、游记、订单或路线链接。
- 粘贴攻略文字。
- 上传攻略截图。
- 导入已购买订单的关键地点和时间。
- 复制已有旅程作为新计划。

用户粘贴第三方平台链接后，寻境直接尝试获取该页面中可合法访问的数据并生成结构化行程草稿。首期重点提取地点、日期、交通、住宿、用餐、预计停留、注意事项和路线意图；保留原始来源链接和获取时间，不把第三方完整正文、图片和评论复制成寻境内容库。

遇到登录限制、页面失效、平台不允许获取或解析失败时，明确提示用户改用复制正文、上传截图或手工补充，不绕过登录、访问控制和反抓取机制。

### 6.2 一键抄作业

处理流程：

1. 识别第三方平台和链接类型。
2. 通过公开页面、平台允许的接口或用户已授权访问方式获取可用数据。
3. 解析页面正文、结构化数据或用户补充的文字和截图。
4. 提取地点、日期、交通、用餐、住宿、预计停留和偏好。
5. 与合规 POI 数据匹配。
6. 标记无法确认、同名歧义、已关闭地点和过期信息。
7. 按天生成候选路线并计算明显绕路、回头路和单日过载。
8. 用户保存或修改后进入自己的旅程。

系统必须展示原始链接、来源平台、获取时间和最近核验时间，不把未经核实的信息包装为实时事实。

### 6.3 路线编辑

支持：

- 按天拖动地点顺序。
- 跨天移动地点。
- 设置交通方式。
- 设置必去、可选和放弃。
- 设置预计停留时长。
- 显示地点间距离、预计时间和过载提醒。
- 对亲子、老人和无障碍需求提供节奏提醒。
- 一键调起第三方地图查看路线。

首期不自研酒店、机票、门票比价和交易。

### 6.4 动态行程预演

该功能吸收 Travel Story 的有效表达方式，但必须服务于真实行程确认。

功能包括：

- 地图按照日期和地点顺序推进镜头。
- 汽车、火车、飞机、步行等载具沿计划路线移动。
- 显示日期、地点、预计距离和交通方式字幕。
- 支持暂停、快进、逐日播放和跳到指定地点。
- 自动识别明显绕路、回头路和单日过载并在播放后提示。
- 输出 15–30 秒竖屏预演和横屏预演。
- 可生成同行查看链接或小程序卡片。

限制：

- 不提供 UFO、火箭等偏演示的虚构交通方式。
- 不把直线飞行动画当作真实道路导航。
- 正式公开输出必须使用合规底图、地图来源和审图号。
- 路线预演是计划，不得标记为真实走过的轨迹。

### 6.5 同行查看与共同记录

支持通过微信链接或小程序卡片邀请同行人：

- 查看行程预演。
- 查看每日路线、地点顺序、时间安排和最新变更。
- 不要求投票，也不要求完成正式确认动作。
- 只看行程时无需获得编辑权限。
- 接受邀请并加入旅程后，可以按需“记下这里”、上传照片和视频、补充语音或一句话备注。
- 每条共同记录显示贡献者，成员可以管理自己上传的素材。
- 旅程创建者负责修改计划、成员管理、作品定稿、印刷和删除整趟旅程。
- 同行查看页默认是私密旅程页：链接可撤销、可重新生成，并显示当前分享范围。
- 行前只展示计划；行中和行后是否展示实际到访由创建者主动选择，默认只展示城市或景区级进度，不展示实时精确经纬度、酒店房间或家庭住址。
- P1 可提供延迟位置分享，允许创建者选择离开地点后或延后 2–24 小时再展示主要到访点。

首期不做复杂多人实时协同编辑，也不做投票和确认流；重点保证“同行看得懂、愿意加入、旅行中能一起留下素材”。

## 7. 行中功能

### 7.1 行中体验原则

默认进入“轻模式”：用户即使整趟旅行没有打开寻境、没有开启定位、没有打卡，也应能在行后通过计划、系统相册原始资产的拍摄时间与位置、视频和共同素材生成首版作品。

- 不把“开始记录”作为进入旅行中状态或行后生成作品的前提。
- 不默认申请持续定位权限；只在用户主动开启轻量记录或完整足迹时，说明用途、采集精度、耗电影响和停止方式后申请授权。
- 不用到站提醒、连续弹窗或任务完成度打扰旅行。
- 行中主操作始终是“查看下一站”和“导航”，记录能力放在次级位置。

### 7.2 今日行程

展示：

- 当前日期、天气提示和今日地点。
- 下一站、预计距离和交通方式。
- 计划地点、可选地点和最新变更。
- 查看详情和一键导航。
- 次级入口中的“记录完整足迹”和“记下这里”。
- 保存旅程后自动缓存当天地点、必要订单卡、备注、同行变更和导航入口；弱网或无网时仍可查看，搜索新地点和实时路况继续交给联网后的第三方服务。

### 7.3 导航调起

首期通过高德等合规地图应用完成转向级导航：

- 从当前地点导航到下一计划地点。
- 用户选择驾车、公交、步行或骑行。
- 返回寻境后继续查看行程；不要求继续任何记录任务。
- 保存“已发起导航”事件，但不把第三方导航路线伪装为本产品自产数据。

寻境不自研实时路况、语音转向和车道级导航。

### 7.4 可选轻量记录与完整足迹

行中位置记录提供三个明确等级，不把专业轨迹记录强加给普通旅行用户：

1. `不记录`：默认选项，行后只使用相册原始资产、计划和用户主动素材重建旅程。
2. `轻量记录`：用户主动开启后，只在打开行程、调起导航、“记下这里”和显著位置变化等必要场景留下位置线索；旅行结束后自动停止。
3. `完整足迹`：面向徒步、自驾、骑行和足迹爱好者的可选增强，需显式开始和结束，支持暂停、继续和丢弃。

共同要求：

- 前台与导航、打卡等当前功能直接相关的短时记录优先；后台记录需单独说明耗电和隐私并获得授权。
- 优先按显著位移和关键事件采集，不使用与业务无关的秒级连续定位。
- 本地先缓存，弱网恢复后批量上传。
- 清洗漂移点、异常跳点和重复点，不把室内或城市高楼间的单个漂移点当作真实到访。
- 完整足迹可计算距离、时长、速度区间和停留点；轻量记录只承诺主要地点与转场线索。
- 持续显示当前记录等级、是否正在记录和预计电量影响。
- 支持整段删除和导出个人数据。
- 未开启、记录中断或轨迹不完整时，不阻断旅行电影和旅行书生成。

隐私默认：

- 不静默启动。
- 不默认公开精确经纬度。
- 家庭住址、酒店和敏感地点支持自动模糊。
- 分享作品只展示地点级或区域级轨迹。

### 7.5 旅程时刻、自动到访推断与“记下这里”

支持：

- 系统按照片时间、地点、停留和用户主动记录自动形成“旅程时刻”，每个时刻可包含地点、照片簇、短视频、贡献者和一句话；用户不需要逐站创建。
- “旅程时刻”是轨迹与旅行故事之间的轻量记录单元，可在行中逐步出现，也可在行后一次重建。
- 行后依据计划、系统相册原始资产的拍摄时间与位置、可选轨迹和其他真实素材自动推断到访地点。
- 用户想主动留痕时，一键“记下这里”，可直接保存地点和时间。
- 用户可选补充照片、一句话、语音或心情，但都不是必填项。
- 计划跳过、临时新增和路过由系统先推断，只有影响叙事的歧义才请用户核对。
- 同一天允许形成多个旅程时刻，不用把酒店、景点、餐厅和转场挤成一条笼统记录。
- 地图和时刻列表双向联动：点选地图上的编号或照片标记，展开对应时刻；点选时刻，地图镜头定位到对应区域并突出同一组素材。
- 用户无需在行中逐站维护时间线；行中看到的是系统逐步整理的结果，行后仍会用原始照片、计划和可选位置线索重新校正。

不默认发送到站打卡提醒，不要求逐站确认、填写原因或选择心情。

### 7.6 可选共同素材

支持：

- 旅行中可从系统相册补充照片、短视频、语音、票根和一句话。
- 同行成员可按需共同上传，并保留贡献者归属。
- 将素材自动绑定到最近时间、轨迹和 POI。
- 用户可手动纠正地点和人物。

行中不要求使用寻境相机，不要求用户写长游记，也不提醒“素材不足”；用户可以全程使用系统相机，旅行结束后再统一选择素材。

## 8. 行后旅程重建

### 8.1 计划与实际对齐

系统自动生成：

- 计划地点与实际到达地点对照。
- 临时新增、取消和绕行。
- 实际停留时间排行。
- 每一天真实的时间线。
- 照片、视频、计划、可选轨迹和可选共同记录的归属结果。

系统只向用户提出 1–3 个会显著影响封面、章节、地点、人名或隐私的高影响问题。低影响且低置信度的细节应使用概括表达或省略，不形成长核对清单，也不允许模型自行编造。

### 8.2 一次选择，原始素材后台上传

用户只做一次素材选择：

1. 从系统相册选择这趟旅行的照片和视频。
2. 原始素材直接在后台上传，用户可以离开页面并随时查看进度。
3. 系统内部自动生成缩略图、预览图和印刷制品，不再要求用户二次补传。

要求：

- 支持 50–500 张原始照片的旅程素材规模。
- 优先通过系统相册选择原始资产；明确展示“使用原图可以更准确地按时间和地点整理”，但不把位置授权变成上传前提。
- 在任何压缩、裁剪、转码或上传前，先在端上尝试读取相册资产和文件中的原始拍摄时间、位置、时区、方向和素材类型。
- 原图保持只读；缩略图、预览图、视频帧和印刷资产全部从原图派生，不回写或覆盖用户原始素材。
- 支持后台上传、分片、断点续传、失败重试和跨会话恢复。
- SHA-256 精确去重。
- 模糊、连拍、曝光、闭眼和近似机位识别。
- 保留原始拍摄时间和 GPS，但不得把 GPS 作为唯一依据。
- 微信转发图、第三方平台保存图、截图、编辑副本和已压缩文件可继续导入，但必须标记为“原始时间或位置可能缺失”，并自动进入降级识别。
- 文件创建时间、修改时间、微信缓存时间和上传时间绝不得冒充原始拍摄时间。
- 用户可随时删除原图和整个旅程。

### 8.3 照片位置可靠性与低操作核对

寻境不使用一个“有 GPS / 无 GPS”标记粗暴决定地点，而是按证据强度使用位置：

| 位置证据 | 产品处理 | 用户操作 |
| --- | --- | --- |
| 用户在地图上确认的地点 | 作为该组素材的最终地点 | 只在必要时确认一次 |
| 系统相册原始资产的位置 | 高可信候选，与时间和行程交叉检查 | 通常无需操作 |
| “记下这里”或导航时的当前位置 | 用于确认当时到访区域 | 主动触发时自动留存 |
| 轻量记录或完整足迹与拍摄时间匹配 | 作为无 GPS 照片的较高可信地点线索 | 仅异常时询问 |
| 同时间照片组、计划、交通和住宿信息 | 先确定城市或片区，不直接确定精确 POI | 需要时按整组确认 |
| OCR、建筑、景观和 POI 视觉识别 | 只生成候选地点和可解释依据 | 高影响且存在歧义时确认 |
| 无可用证据 | 标记“地点未确定”，用概括文字或省略地点 | 不强制补录 |

可靠性规则：

- 每个被采用的地点在系统内部都必须保留来源、原始或推断属性、精度与可信级别；不向普通用户暴露内部分数和字段。
- 相册位置也不是绝对事实，需检查定位漂移、编辑修改、连续照片地点冲突、不可能的短时跨城移动和与旅程日期不符。
- 火车、飞机、汽车等移动途中的照片可归入转场章节，但不得因为路过某地就生成“到访”。
- 同一时间段和地点的照片先组成素材簇，系统一次确认整组，不逐张询问。
- 定位覆盖较低时，优先确认“日期 + 城市 / 景区”，不追求伪精确的经纬度和具体店铺。
- 所有地点确认与其他高影响问题共用整趟旅行 1–3 个问题的上限，不另行生成长位置清单。

用户只看到简单结果，例如：

> 已整理 156 张照片、6 个主要地点；118 张具有原始位置，31 张已通过时间和行程归类，7 张暂不确定。

需要核对时，使用“这组 32 张照片可能拍摄于什刹海，是否正确？”这类地点组问题，提供“正确”、“在地图上修改”和“暂不确定”三个动作。

### 8.4 自动组织为故事章节

系统在后台把素材组织成以下故事章节，不要求用户逐项归类：

- 开场与出发。
- 交通与转场。
- 地点到达。
- 人物互动。
- 风景高潮。
- 意外变化。
- 告别与返程。

每个章节必须保留内部证据来源和置信度；只有高影响不确定项向用户提问，其余不展示内部结构。

### 8.5 路线补全与修复

系统可以发现轨迹中断、异常跳点、不可能的短时跨城移动和缺失转场，并给出可解释的修复建议：

- P0 只自动清洗明显错误点，并使用照片、计划和交通信息重建主要地点顺序；不伪造连续轨迹。
- P1 支持整段接受或拒绝候选补全、移动或删除错误点，以及导入和导出 GPX。
- 原始 GPS、用户确认结果和系统推断分别保留；任何修复都不得覆盖原始证据。
- 飞机、火车等长距离转场可以用示意线表达，但必须标注为交通转场，不宣称为实际连续定位。

实际旅程和旅行书中的路线必须按证据类型显示，不以一条漂亮但虚假的连续线覆盖差异：

| 路线证据 | 默认画法 | 可向用户表达的含义 | 禁止表达 |
| --- | --- | --- | --- |
| 轻量记录或完整足迹的有效连续点 | 青绿色实线 | 设备记录到的轨迹片段 | 精确道路导航或运动级测量 |
| 两组可靠照片位置之间的顺序关系 | 珊瑚色点线，端点显示照片或地点 | 根据照片时间和位置还原的到访顺序 | 实际连续走过该线 |
| 已知飞机、火车、汽车等交通转场 | 灰色虚线并显示交通方式 | 两个地点之间发生过该类转场 | 车辆真实行驶路径 |
| 只有城市、片区或单个可靠地点 | 区域、地点卡或单点，不连线 | 在该区域留下过素材 | 伪造 POI、经纬度或完整路线 |
| 无可靠位置证据 | 不画线、不下精确点 | 地点暂不确定 | 为了页面完整自动补线 |

点选任一路段时，只显示“轨迹记录 / 照片位置 / 交通衔接 / 地点未确定”等用户可理解的证据标签，不展示技术置信分数。公开分享、旅行电影和印刷地图都使用同一套语义，不能在不同制品中把推断路线升级成真实轨迹。

## 9. 寻境电影

### 9.1 产品定位

旅行电影是分享和增长输出，不替代旅行书，也不发展成专业剪辑软件。

### 9.2 自动生成

功能包括：

- 优先使用核对后的实际地点；有完整轨迹时增强地图动画，无轨迹时仍可根据照片时间与地点生成。
- 镜头沿时间线推进。
- 交通动画、地点字幕、日期和里程。
- 插入照片和短视频。
- 生成开场、章节、转场和结尾。
- 支持竖屏 9:16 和横屏 16:9。
- 首期以 720p/1080p 输出为主。
- 保留地图来源、必要标识和生成信息。

### 9.3 计划电影与回忆电影

两者必须明确区分：

| 类型 | 用户可理解的数据来源 | 文案标识 | 用途 |
| --- | --- | --- | --- |
| 计划电影 | 用户保存的每日计划和交通安排 | “我们的旅行计划” | 行前确认和邀请 |
| 回忆电影 | 行后重建的实际地点和真实素材，完整足迹仅作可选增强 | “我们真正走过的旅程” | 行后分享和召回 |

### 9.4 轻量修改

用户只需要：

- 更换封面。
- 隐藏某个地点或人物。
- 删除片段。
- 调整整体节奏：更短、更温暖、更有活力。
- 重新生成字幕。

首期不做帧级时间轴、复杂滤镜和多轨音频编辑。

### 9.5 路线回放增强

- P0 同时提供可交互的“完整旅程回放”和可导出的固定模板回忆电影；前者负责沉浸回看，后者负责社交平台分享，两者使用同一份实际旅程和素材证据。
- 完整旅程回放按“整趟概览 -> 按日进入 -> 逐时刻推进 -> 旅程总结”组织，不直接从一张静态总图跳到导出视频。
- 地图镜头、路线进度、当前日期、当前时刻卡和照片/视频必须同步；播放到某个时刻时，地图突出对应标记和路段，点击标记或时间轴也能跳到同一时刻。
- 播放器支持播放/暂停、前后时刻、按日或按时刻拖动、0.5×/1×/2×速度，以及直接跳到指定日期或地点；默认自动播放不超过 60 秒，用户可继续逐日查看完整内容。
- 当前时刻卡至少显示时间、地点或区域、交通方式、素材数量和一句真实摘要；有贡献者时显示共同记录人，但不自动公开儿童姓名或敏感关系。
- 实线轨迹、照片位置点线、交通衔接虚线和未知断点必须沿用第 8.5 节规则；未开启轨迹时也能回放地点和时刻，但不得补成道路级连续线。
- 回放结束页展示天数、主要地点、照片数量和作品入口，主动作按场景提供“分享回忆电影”或“继续翻阅旅行书”，不把统计本身做成重度分析产品。
- P1 只在真实路线数据覆盖足够时提供 3D 飞越、海拔曲线和按交通方式统计；数据不足自动降级到 2D 地点回放。
- 3D 回放是分享和回忆增强，不作为成书前提，也不单独发展成专业轨迹产品。

## 10. 寻境旅行书

### 10.1 首版生成

处理流程：

1. 素材清点、去重和质量判断；在任何压缩或转码前读取原始拍摄时间、时区、位置、方向、尺寸和素材类型。
2. 先按拍摄时间形成事件序列，再结合可靠位置、计划、轨迹、视觉相似度和人物关系形成照片簇；时间被编辑或位置缺失时保留降级标记。
3. 选片并记录选择理由和备选照片；截图、重复、模糊和明显误触只从首版候选中排除，不删除原文件。
4. 形成叙事主线、章节和整本节奏，不让连续页面重复同一种拼贴结构。
5. 生成封面、路线总览、地图分隔、日期/章节开场、主图跨页、照片序列、正文和结尾。
6. 对派生图执行可撤销的曝光、色彩和裁切优化；不覆盖原图，不对人物、地点或纪实内容进行无提示重绘。
7. 自动完成事实置信度、重复照片、裁切、字体、出血、DPI、缺图、地图来源和敏感地点检查。
8. 仅在存在高影响不确定项时向用户提出 1–3 个问题；普通细节由系统概括或省略。
9. 自动生成用户可翻阅的完整首版和“整本节奏”缩略总览；只有自动质检失败或命中高风险规则时才进入例外人工审核。

旗舰样书验收不使用少量演示照片冒充完整能力，首批正式样书应使用至少 100 张真实唯一照片。

### 10.2 用户翻阅与修改

支持：

- 手机或浏览器整本翻阅。
- 查看单页和跨页。
- 从“整本节奏”总览查看封面、路线总览、章节开场、主图跨页、拼贴、连续镜头、安静文字、地图分隔和结尾，并可一键跳页。
- 付款前可完整翻阅低清或带保护标识的首版，不用盲买；付款并确认后获得高质量数字版和实体书。
- 替换照片、隐藏地点和修改人名。
- 对照片簇、旅程时刻或章节进行批量隐藏与恢复，不要求逐张处理。
- 集中展示低清、重复、位置不确定、重要人物缺失和文字溢出等异常，并提供“一键接受系统建议”或单项修改。
- 输入自然语言修改整本或单页。
- 对当前页面可从系统给出的 2–3 个印刷安全备选版式中“换一个版式”；不展示无限模板市场，也不要求用户重新排全部照片。
- 修改前显示受影响页面。
- 保留版本列表、下载和回退。
- 用户明确确认印刷校样。

默认让用户直接看到完整首版，不先要求选模板、逐页锁定或核对长清单。模板作为内部印刷安全布局；自然语言改单是可选能力，不是完成订单的必经步骤。

### 10.3 地图页与整书排版规则

地图不是装饰页，而是整本书的空间目录、章节分隔和地点证据。系统按以下门槛自动决定地图用法：

| 位置覆盖 | 自动排版结果 | 用户需要做什么 |
| --- | --- | --- |
| 至少 2 个可靠地点组，且顺序可确认 | 生成路线总览或章节地图；路线按第 8.5 节区分实线、点线、虚线和断点 | 通常无需操作 |
| 只有 1 个可靠地点组 | 生成地点卡、区域小图或章节落点，不生成完整路线 | 无需补经纬度 |
| 只有城市/片区级证据 | 使用区域轮廓、城市名或“这一日”章节，不放精确 POI | 高影响时按整组确认 |
| 无可靠位置 | 省略地图，以时间、人物或事件组织章节 | 不强制补位置 |

排版必须形成整本节奏，而不是逐页随机拼图：

1. 推荐顺序为“封面 -> 路线总览 -> 章节开场 -> 主图跨页 -> 双图/三图叙事 -> 拼贴 -> 连续镜头 -> 安静文字 -> 地图分隔 -> 结尾”，系统根据素材自动取舍，不要求每本机械包含全部页型。
2. 同一种页面结构默认不连续出现超过 2 个跨页；章节开场与视觉高潮之间保留疏密变化。
3. 叙事页默认不超过 6 张照片；只有索引、联系表或用户明确要求时才允许更高密度，避免把“最多可放”误当成“最好多放”。
4. 日期和地点作为章节信息只在需要处出现，默认每个日期或章节标题出现一次，不在每页重复制造噪声。
5. 竖图、横图、全景、连续镜头和近似照片分别进入适配页型；换版式只在 2–3 个通过裁切、出血和文字安全检查的候选中切换。
6. 地图、照片和正文的颜色、字体、留白与书型统一；地图页可作为整页或跨页章节分隔，但敏感地点和不确定地点不因版式需要被强行展示。
7. 整本总览必须显示页数、章节数、地图页数和需确认问题数，让用户先判断整本节奏，再决定是否查看例外；不要求逐页点确认。

### 10.4 首测商品

首期只验证一个标品：

- A5 竖版。
- 48 页基准，可在明确规则下增减页。
- 硬壳或经真实供应商确认的主力装帧。
- 完整电子版随实体书交付。
- 建议测试价 169–199 元，最终价格按印刷、物流、支付、模型、人工和售后成本倒推。
- 用户看到完整首版和明确商品规格后一次付款；标准商品不拆分定金和尾款。

第二本加印、礼盒、人工精修和正式出版服务不进入首期主流程。P1 在标准书型履约稳定后增加第二本加印、礼赠地址，并只从 Lay-flat 或礼赠型中选择一个第二书型试验，不同时扩张多种尺寸、装帧和纸张。

### 10.5 自动质检与例外审核

标准旅行书不得依赖运营人员逐页核对。系统自动执行：

- 原始素材完整性、重复和损坏检测。
- 模糊、曝光、闭眼、裁切风险和有效分辨率检测。
- 字体嵌入、溢出、出血、DPI、页数、缺图和重复版面检查。
- 关键人名、日期、地点、地图来源、敏感位置和内容安全检查。
- 输入素材、版本、PDF、印刷清单和页面渲染结果的哈希与审计记录。
- 整本节奏检查：连续重复页型、章节开场缺失、视觉高潮过密/过疏、日期标题重复和空白页异常。
- 地图证据检查：无可靠位置时生成精确点、照片推断线被画成实轨、坐标系混用、敏感地点未模糊或地图来源缺失均阻断发布。

只有以下情况进入人工例外队列：自动质检失败、关键事实无法自动解决、地图或内容存在高风险、用户投诉，以及用户明确购买人工精修服务。首测目标是假设至少 80% 的标准订单无需运营人员逐页调整即可进入用户首版；若人工逐页调整订单比例超过 30%，产品不得扩大规模，应优先重构生成与质检能力。

### 10.6 印刷履约

功能包括：

- 收货地址和发票信息。
- 印刷校样确认。
- 印刷任务和供应商状态。
- 物流单号。
- 签收和售后。
- 质量问题重印。
- 订单退款、售后责任和重印记录。

实体定制印品和正式公开出版必须分开管理。涉及公开发行、书号、公开销售或出版地图时，必须进入出版社和持证印企流程。

## 11. 作品与家庭旅行档案

### 11.1 作品库

按旅程展示：

- 计划电影。
- 真实足迹。
- 回忆电影。
- 旅行故事。
- 旅行书版本。
- 订单和物流。

### 11.2 我的足迹

“我的足迹”先从用户已经完成作品的旅行自动形成，不要求补录历史：

- 展示用户主动保存的旅行地点。
- 显示旅行次数、城市、照片数量、作品数量和已成书次数。
- 从单次旅行进入对应路线、电影、故事和旅行书。
- 默认不公开精确轨迹。
- P1 在用户至少有两趟已完成旅程后生成年度回顾和年度成书入口；只有一趟旅程时不展示空洞的年度统计，也不以足迹数量作为首期付费价值。

### 11.3 家庭旅行档案

家庭旅行不是公开社区，而是围绕真实共同旅行形成的私密档案：

- 用户可以把一趟旅行加入家庭档案。
- 同行人只在获得邀请后查看共同旅行和公开给自己的作品。
- 创建者可以控制原图、精确位置、人物和书稿的可见范围。
- 支持家庭成员共同补充照片，但不要求实时协同编辑书稿。
- 支持第二本加印、赠送地址和家庭纪念日提醒。
- P1 支持按年度把多趟旅行汇总为家庭旅行年鉴。

后台至少包含：

### 12.1 用户与旅程

- 用户、成员和隐私授权。
- 旅程状态、异常和删除请求。
- 计划路线、可选真实轨迹和素材归属核对。

### 12.2 内容与生成任务

- 第三方链接获取与攻略解析任务。
- POI 匹配和人工纠错。
- 计划电影任务。
- 旅行电影任务。
- 成书任务、版本和制品。
- 自动质检结果和例外审核队列。
- Codex Harness 运行实例、队列、任务阶段、重试、取消和标准化错误。
- 模型、Codex SDK/Harness、`travel-memory-book` Skill、模板、渲染器和 QA 版本，以及 Skill 真实加载状态和哈希。

### 12.3 订单与履约

- 支付、退款和支付流水。
- 印刷供应商、任务和异常。
- 物流和签收。
- 售后和重印。

### 12.4 用户服务与内容运营

- 帮助中心、隐私说明和关键操作引导。

### 12.5 质量看板

- 单次原始素材上传成功率和平均耗时。
- 系统相册原始资产导入比例，以及不同导入渠道的原始拍摄时间、直接 GPS 和时区可用率。
- 位置证据来源分布、地点组自动归类准确率、用户批量修正率和位置错误投诉率。
- 文件缓存或上传时间误当拍摄时间的次数，目标必须为 0。
- 无原始位置时的旅程重建成功率和每趟旅行的位置核对问题数。
- 可选足迹记录成功率，不作为主漏斗转化条件。
- 轻量记录与完整足迹的附加耗电、异常中断率和旅行结束后自动停止成功率。
- 素材自动归属准确率。
- 电影和成书生成成功率。
- Codex Harness 可用率、任务排队/长尾耗时、模型 token 与成本、Skill 加载失败数、当前 Skill 版本/哈希和最近灰度/回滚。
- 无轨迹、无打卡情况下的首版生成成功率。
- 人工介入率和人工逐页调整比例。
- 两轮内定稿率。
- 印刷准时率、重印率和退款率。

## 13. 系统边界与技术形态

### 13.1 客户端

- H5/小程序：作为低摩擦获客与同行查看入口，承接双入口建旅程、攻略导入、计划预演、作品翻阅、付款和订单查询。可支持原始素材上传，但对拍摄时间和位置只做最大能力保留，不承诺第三方容器、转发图和临时文件一定具有原始元数据。
- UniApp APP：作为高可信原图导入和行中记录的推荐载体，P0 完成系统相册原始资产选择、端上元数据读取、弱网上传、今日行程、导航调起和轻量记录，P1 再增强完整足迹。用户不安装 APP 仍可完成首单，但系统需如实展示位置证据覆盖与降级结果。
- Web/SVG 翻阅器：整本翻阅、自然语言修改和版本对比。

### 13.2 服务端

- Yudao：账户、租户、权限、订单和运营控制面。
- Trip Core：统一承接计划、可选轨迹、“记下这里”和旅程事件。
- Media Service：原始素材对象存储、内部缩略图与预览制品、去重和删除。
- Story Engine：事件重建、叙事、电影和旅行书计划。
- Publication Harness Runner：由现有 Memory Book Worker 演进，在服务器隔离任务中运行 Codex Harness，加载锁定的 `travel-memory-book` Skill 完成旅程理解、选片、跨页叙事和可控修订。
- Render/QA Worker：以确定性代码生成视频、SVG、PDF、预览图和 QA 制品，决定机械印前是否合格。
- Fulfillment Adapter：印刷、物流、售后和供应商对账。

### 13.3 生产要求

- 原图使用对象存储和签名 URL，不以 Worker 本地目录作为生产存储。
- 生成任务进入持久队列，支持幂等、重试、限流和取消。
- 每个制品记录输入范围、引擎版本、模型版本和 SHA-256。
- 每个成书任务同时记录 Worker 镜像、Codex SDK/Harness、模型、推理强度、`travel-memory-book` Skill 版本/哈希、渲染器和 QA 版本。
- Skill 未加载、版本/哈希不符、制品缺失或 QA 失败时必须 fail closed；只有用户确认且确定性 QA 通过才可 `PRINT_READY`。
- Harness 每任务使用非特权隔离工作区，原图只读，不持有订单、支付或用户主库写凭据。
- 用户删除后必须执行素材、缓存、派生文件和备份保留策略。
- 公开接口必须有身份验证、租户隔离、速率限制和审计日志。

## 14. 合规与安全要求

### 14.1 位置与个人信息

- 精确位置及其组成的行踪轨迹按敏感个人信息处理。
- 照片位置读取、轻量记录和完整足迹分别说明产品用途、采集范围、保存时间和对用户权益的影响，在对应功能被主动使用时再请求所需最小权限。
- 轨迹采集需要特定目的、充分必要性和单独同意；不能因用户拒绝位置或相册精确位置授权而阻断旅行书基本生成。
- 对可选轻量记录和完整足迹明确展示开始、当前记录等级、暂停、结束和删除入口；旅行结束后不得继续后台记录。
- 精确坐标不进入普通运营日志、增长埋点和对外分享文案；公开作品、分享页和实体书默认只使用城市、景区、区域级地点或模糊轨迹。
- 家庭住址、酒店、医疗地点和其他敏感停留点默认隐藏或模糊，只有用户明确选择时才可进入私密作品。
- 儿童照片和未成年人信息需要监护人授权和更严格保护。
- 用户可查阅、导出、更正和删除个人数据。
- 不使用用户原图进行未授权训练。

### 14.2 地图

- 线上地图使用合法地图服务和经审核图源。
- 展示地图来源和审图号。
- 不擅自修改国界、行政区划和重要地理要素。
- 正式印刷地图页进入地图审核和出版检查流程。
- 计划路线与真实轨迹使用不同视觉和文字标识。
- 保留照片与设备提供的原始 GPS 坐标及其坐标系信息；转换为国内地图展示坐标时不得覆盖原始证据。
- 坐标转换后必须保留地图服务方与转换结果的内部追溯信息，并对 WGS84、GCJ-02 等坐标系混用设置发布阻断检查。

### 14.3 生成内容

- 用户服务协议说明生成内容及修改责任。
- 公开分享的生成文本、图片和视频按要求保留显式或隐式标识。
- 事实性地点、人名、日期和文化知识必须可核对。
- 用户拥有最终确认权，不允许模型自动提交印刷。

### 14.4 印刷与出版

- 首期按定制纪念印品与合规印企合作。
- 不把按需印刷直接宣传为取得书号的正式出版物。
- 公开发行、销售出版物或使用书号时单独走出版社流程。

### 14.5 第三方链接与内容来源

- 只有用户主动粘贴链接或发起导入后，才获取对应页面数据。
- 仅使用平台公开允许访问的数据、正式接口或用户已授权访问的数据。
- 不绕过登录、付费墙、验证码、访问控制和反抓取机制。
- 输出保留原始链接、来源平台和获取时间，方便用户回看和核对。
- 不把第三方完整正文、图片、视频和评论沉淀为寻境自有内容库。
- 平台规则、授权或页面结构变化时，对应链接适配器可以立即停用，并回退到正文粘贴或截图导入。

## 15. 功能优先级

完整产品范围由前述六个闭环构成；优先级表示落地顺序，不表示低优先级能力可以用概念页冒充可用功能。P0 必须让六个闭环各有一条真实路径，P1/P2 再增加深度、自动化和规模。

### 15.1 P0：完整 C 端可试运营产品

- 新用户“规划新旅行”和“旅行结束做作品”双入口。
- 创建旅程、第三方链接获取和攻略导入。
- 地点提取、POI 匹配和路线确认。
- 两至三套稳定的动态计划行程预演及竖屏分享。
- 同行免安装查看、可撤销的私密旅程页、加入旅程和共同补充素材；实际位置默认只展示城市或景区级进度。
- 可离线查看的今日行程、第三方导航调起、“记下这里”和用户主动开启的轻量记录。
- 按时间、地点和照片簇自动形成“旅程时刻”，不要求逐站打卡或写游记。
- APP 系统相册原始资产选择、压缩前拍摄时间与位置读取、位置证据覆盖展示和异常检查。
- 无行中操作情况下，根据相册原始资产、计划和视觉证据重建旅程；微信转发图等无元数据素材有明确降级路径。
- 按时间和地点形成素材簇，只对高影响歧义进行地点组批量确认，不逐张询问。
- 行后直接从照片识别旅程，以及轻量计划与实际对齐。
- 原始素材一次选择、后台上传和内部预览制品。
- 旅行故事、足迹卡和固定模板的竖屏回忆电影。
- 地图、时间轴、旅程时刻与媒体同步的 2D 完整旅程回放；支持按日/时刻跳转、播放控制和证据类型路线表达。
- 旅行书自动完整首版、整本节奏总览、证据驱动地图页、2–3 个安全备选版式、集中异常提示、批量隐藏与恢复、自动质检、例外审核、自然语言修改、版本和印刷校样。
- 服务器 Codex Harness 真实加载锁定的 `travel-memory-book` Skill，生成过程、版本、制品和 QA 可追溯，并支持灰度与回滚。
- 单一标准书型、一次付款、印刷、物流和售后。
- 作品库和基于已完成旅行形成的基础个人足迹。
- 支撑上述链路的生成任务、质量、订单、履约和用户服务后台。

### 15.2 P1：增强记录、分享和家庭留存

- 横屏旅行电影。
- 用户主动开启的完整足迹、弱网上传和低功耗后台记录增强，以及徒步、自驾和骑行等专项模式。
- 延迟位置分享、路线修复建议、GPX 导入导出、交通方式统计和数据充分时的 3D 实际路线回放。
- 共同记录的成员权限、素材归属和退出旅程增强。
- 人物关系核对。
- 礼赠、第二本加印，以及在标准书型稳定后只试验一个第二书型。
- 家庭旅行档案、纪念日提醒和家庭年鉴入口。
- 城市足迹、年度回顾和多趟旅行汇总。
- 内容安全与地图例外审核工作台。
- 多供应商印刷比价和自动派单。

### 15.3 P2：内容深度与商品扩张

- 全球足迹和更完整的年度旅行报告。
- 多人共同编辑旅行书。
- 情侣、毕业和银发细分商品。
- 高级电影主题和更多受控书型。
- 城市目的地内容包。
- 正式出版服务。
- 海外地图、跨境印刷和多语言。
- 经过多次旅行留存验证后的可选订阅、高级地图主题和更多统计。
- 经过分享带新客验证后的公开旅行灵感库或精选案例库。

### 15.4 明确不做

- 自研完整地图、实时路况和转向级导航。
- 酒店、机票、门票预订平台。
- 攻略内容社区和大规模第三方内容抓取。
- 专业视频时间轴编辑器。
- 泛家庭云相册和全部人生照片管理。
- 默认持续后台定位、运动级秒级轨迹、救援或安全保障承诺。
- 预算、分账、打包清单和通用旅行待办。
- 空白画布式专业书稿编辑器，以及首期同时上线多尺寸、多装帧、多纸张和多类印品。
- 当前阶段的合作方后台、加盟、渠道分润和结算。
- 在真实支付未验证前继续扩大地图商店和 B/G 定制平台范围。

## 16. 商业指标与生死门槛

### 16.1 北极星指标

> 每月完成旅行后付费并成功交付的旅行书数量。

### 16.2 双入口全漏斗

```text
小红书 / 抖音 / 视频号 / 自然访问
  -> 入口 A：导入计划 -> 动态预演 -> 完成旅行
  -> 入口 B：旅行已结束 -> 直接选择原始素材
  -> 两个入口汇入实际旅程重建
  -> 自动生成行后回顾、旅行电影和旅行书首版
  -> 打开旅行书首版
  -> 少量修改并确认印刷校样
  -> 一次付款
  -> 签收
  -> 进入旅行档案、晒单、推荐或加印
```

### 16.3 关键指标

- 第三方链接获取成功率、攻略解析成功率和行程保存率。
- 计划预演生成率、分享率和同行打开率。
- 私密旅程页打开率、链接撤销成功率和实际进度分享启用率。
- 用户在无强制行中操作下完成旅行的比例。
- 单次原始素材选择后的上传完成率。
- 系统相册原始资产导入率、原始拍摄时间覆盖率、直接 GPS 覆盖率和位置证据来源分布。
- 每趟旅行地点组确认次数、用户位置修正率和位置错误投诉率。
- 无轨迹、无打卡情况下的首版生成成功率。
- 旅程时刻自动形成成功率，以及用户主动新增或修改时刻的比例；后者过高说明自动重建质量不足。
- 可选完整足迹启用率和成功率，仅用于评估增强价值。
- 行后回顾打开率。
- 完整旅程回放打开率、完成率、按日/时刻跳转率，以及回放后分享电影或翻阅旅行书的转化率。
- 旅行电影分享率。
- 首版打开率和全款转化率。
- 整本节奏总览打开率、地图地点整组修正率、用户换版率，以及首次自动首版中需人工重排的页面比例。
- 两轮内定稿率。
- 每单高影响核对问题数、人工介入率和人工逐页调整比例。
- 单本贡献毛利。
- 印刷准时率、重印率和退款率。
- 按小红书、抖音、视频号和自然访问区分的上传、付款与签收订单数。
- 作品再次打开、第二本加印和用户主动分享率，作为长期价值指标而不是首期日活目标。

### 16.4 首轮决策门槛

以 50 个有效旅行用户为第一轮样本：

- 少于 5 个付费订单：停止扩大通用 C 端 APP。
- 有付费但超过 30% 的标准订单需要人工逐页调整：停止扩大，优先重构生成、事实核对和自动质检；人工精修只能作为独立增值服务，不能托底标准商品。
- 至少 10 个真实付费、80% 的标准订单无需运营人员逐页调整、80% 两轮内定稿、退款和重印低于 5%，且贡献毛利为正：进入扩大 C 端获客和 P1 增强阶段。

计划电影本身不作为付费成功指标。若预演分享率和同行打开率持续低，应缩减动画编辑功能，不继续建设复杂编辑器。

## 17. 12 周实施顺序

12 周是建立在复用现有 UniApp、Yudao、轨迹、成书 Worker、SVG/PDF 和机械 QA 资产，并具备产品设计、前端、后端/媒体、生成渲染和 QA 并行能力之上的目标周期。如果实际只有单线开发资源，必须延长到 16–20 周或减少 P0 深度，不允许用 mock、硬编码案例或人工后台冒充完整交付。

### 第 1–2 周：产品冻结、真实样本与履约锁定

- 冻结非主线地图商店和 B/G 功能扩张。
- 在配套文档中确认统一旅程数据模型和各模块状态机。
- 用至少 3 趟、每趟 100 张以上真实照片制作样书。
- 至少包含 1 趟完全没有寻境轨迹和打卡数据的样本。
- 真实样本覆盖 iOS 与 Android 系统相册原图、编辑副本、截图、微信转发图和第三方平台保存图，形成拍摄时间与位置可用性基线。
- 取得真实印刷、物流和售后成本。
- 锁定一个标准书型、印刷文件规范、付款规则、退款和重印责任。
- 完成地图、位置、印刷和生成内容合规确认。

### 第 3–5 周：行后成书与真实交易底座

- 完成双入口首页，其中“旅行结束做作品”先打通真实主链路。
- 原始素材一次选择、压缩前元数据读取、后台上传和失败恢复。
- 完成位置证据覆盖展示、异常检测、地点组批量确认和无元数据降级路径。
- 基于相册原始资产、计划、可选位置记录和视觉证据完成实际旅程重建。
- 完成旅行书首版、真实翻页、保护性预览、集中异常提示、批量隐藏与恢复、自然语言轻改、版本和自动质检。
- 将 `travel-memory-book` Skill 作为服务器 Codex Harness 的锁定生产依赖，补齐发现、加载证据、不可变版本、持久任务、隔离执行、灰度和回滚。
- 完成整本节奏总览、证据驱动地图页、受控页型组合和位置不足时不生成伪路线的降级规则。
- 完成一次付款、印刷、物流、退款、重印和用户删除。
- 先用 5–10 个真实订单验证首版质量、人工介入时间和履约成本。

### 第 6–8 周：行前预演与轻行中闭环

- 打通真实第三方攻略链接、正文和截图导入及失败回退。
- 完成路线核对、两至三套动态行程预演，以及可撤销、默认不公开实际精确位置的同行免安装私密旅程页。
- 完成可离线查看的今日行程、第三方导航调起、“记下这里”和用户主动开启的轻量记录。
- 自动形成可在行中出现、也可在行后重建的旅程时刻。
- 同行可以加入旅程并补充素材，但不建设复杂实时协同。
- 验证用户完全不使用行中功能时仍能正常获得作品。

### 第 9–10 周：数字作品与个人旅行档案

- 生成旅行故事、足迹卡、地图/时刻同步的 2D 完整旅程回放和固定模板竖屏回忆电影。
- 对同一旅程明确区分计划电影和真实回忆电影。
- 完成作品库、基础个人足迹和订单关联。
- 接入小红书、抖音、视频号来源标记，追踪到上传、付款和签收。
- 完成平台生成任务、例外审核、订单履约和质量看板。

### 第 11–12 周：C 端产品收口与放量门禁

- 完成两个入口、六个闭环和平台后台的端到端回归。
- 邀请 30–50 名具有真实旅行计划或足量旅行照片的用户完成全链路验证。
- 验证小红书、抖音、视频号内容来源到上传、付款和签收的可归因链路。
- 完成弱网、权限拒绝、上传中断、生成失败、退款和重印等异常验收。
- 形成首期真实订单、人工介入时间和单本贡献毛利报告。
- 未达到第 16.4 节门槛时不扩大投放，也不进入合作方产品建设。

- 公益报告和政府汇报系统。

### 19.1 四类标杆分别解决什么问题

### 19.2 跨产品共同规律

- 旅行是低频事件，不应以日活或每天打卡为前提，应以每趟 Trip 的作品生成、分享、付费和加印衡量。
- 被动采集优先于主动记录；寻境必须进一步保证“没开轨迹、没打卡也能成书”。
- 自动首版优先于模板选择，用户只处理少量高影响错误和个人偏好。
- 路线视频和私密旅程页负责分享增长，实体旅行书负责首期付费，长期档案负责复访。
- 隐私、路线错误修复和印刷异常提示必须是显性产品功能，不能依赖后台人工解释。
- 竞品功能多不等于寻境应该全部复制；只有能增强“攻略导入、无负担记录、真实重建、分享和成书”主链路的能力才进入优先级。

### 19.3 Travel Story 的实现参考

参考项目：`https://github.com/wang-bool/Travel-Story`

值得借鉴：

- 按天播放行程。
- 地图镜头跟随路线推进。
- 不同交通方式的视觉表达。
- 横屏、竖屏视频输出。
- MapLibre、Turf、WebCodecs、MediaRecorder、FFmpeg 的实现组合。

不直接照搬：

- 单用户自部署模式。
- 本地 `data/media` 存储。
- 无账号和 API 鉴权。
- 用户逐个地点手工挂载素材。
- 把计划路线当作真实旅行。
- 免 Key 高德栅格瓦片或未明确商业授权的公开图源。
- 娱乐化虚构交通方式。

如复用 MIT 代码，应保留许可证和归属说明，并对地图来源、商业授权、坐标体系、隐私、性能和移动端兼容性重新验收。

## 20. P0 产品验收标准

P0 只有在以下链路全部真实完成后才可称为可试运营：

1. 新用户可以分别从“规划新旅行”和“旅行结束做作品”进入，两条路径最终形成同一结构的旅程和作品，而不是两个孤立模块。
2. 用户粘贴一条真实第三方平台攻略链接并生成可保存路线；无法获取时能明确回退到正文粘贴或截图上传。
3. 用户播放计划行程，修改路线后再次播放，变化正确；输出可以在手机端稳定查看和分享。
4. 同行人可通过可撤销的私密手机链接查看计划，无需投票或确认；加入旅程后可按需上传带贡献者归属的素材；未主动开启实际进度分享时不展示实际路线，已分享时也默认不展示实时精确经纬度。
5. 用户可在弱网或无网时查看已保存的今日地点、必要订单卡、备注和导航入口，联网后调起真实第三方导航并使用“记下这里”；轻量记录只有用户主动开启后才运行，旅行结束后自动停止；定位被拒绝或功能未使用时，不阻断后续作品生成。
6. 用户旅行中不开始轨迹、不打卡、不写备注，或者旅行结束后直接进入，系统仍能基于系统相册原始资产、计划和视觉证据生成可核对的实际旅程。
