## 1. AI 接手目标

把现有分散的攻略导入、路线、轻记录、作品和旅行书能力收敛成完整 C 端“寻境”，真实打通：

```text
双入口 -> 同一个 Trip -> 行前/行后数据 -> 数字作品
-> 旅行书完整预览 -> 一次付款 -> 印刷物流售后 -> 作品档案
```

当前不做合作方、加盟、分润和结算。不要把目标缩成单页照片书，也不要把所有能力同时铺开成无法验收的大改造；必须按本任务书的垂直切片顺序完成。

## 2. 执行协议

### 2.1 每次开工前

```bash
pwd
git status --short
git branch --show-current
git remote -v
git fetch github main
git fetch origin main
git rev-list --left-right --count HEAD...github/main
git rev-list --left-right --count HEAD...origin/main
```

然后完整阅读 `AGENTS.md` 和本页顶部四份权威文档。

如果工作树存在其他人的修改：

- 不执行 `git reset --hard`、`git checkout --`、批量格式化或清理未跟踪文件。
- 优先创建独立 `codex/<task-id>-<slug>` 分支或 clean worktree。
- 只暂存当前任务明确列出的文件。
- 遇到写路径重叠，先停止任务并交接，不自行合并别人的未提交实现。

### 2.2 每次只领取一个任务 ID

任务开始时在独立执行台账中把状态从 `TODO` 改为 `IN_PROGRESS`，写入分支和执行者；任务书本身保持稳定。完成后把台账改为 `DONE`，附提交哈希与证据路径。若依赖、凭据、供应商或环境缺失，状态写 `BLOCKED_ENV`，不得伪造成功。

允许状态：

- `TODO`：依赖未满足或尚未开始。
- `IN_PROGRESS`：已有唯一执行者和分支。
- `BLOCKED_ENV`：缺少外部环境、凭据、供应商或真实数据。
- `BLOCKED_CONTRACT`：产品、对象或接口口径冲突。
- `DONE`：代码、测试、用户验收和证据全部完成。

### 2.3 完成一个任务必须提交

1. 实现代码和必要迁移。
2. 自动化测试。
3. 至少一条真实用户操作验收；纯后端任务至少提供真实 API/数据库证据。
4. `qa/xunjing-c-product/<YYYYMMDD>/<TASK-ID>/README.md` 证据索引。
5. 执行过的命令、结果、已知限制和下一任务 handoff。
6. 只包含该任务范围的 Git 提交。

### XJ-C1-01 统一 Trip/计划/成员服务端底座

**目标**

在 `yudao-module-xunjing` 建立与 v1.2 一致的 `Trip`、`TripMember`、`TripInvite`、`PlanSource`、`PlanVersion` 及计划明细持久化，让行前和行后入口使用同一个聚合根。

**主要路径**

- `backend/yudao/yudao-module-xunjing/src/main/java/.../controller/app/trip/`
- `.../service/trip/`、`.../dal/dataobject/trip/`、`.../dal/mysql/trip/`
- `backend/yudao/sql/mysql/xunjing-module.sql`
- Yudao 测试 SQL 和单元测试

**实现要求**

- 使用 DTO/VO 和稳定错误码，不使用 `Map<String,Object>`。
- 支持行前 `DRAFT -> UPCOMING`，也支持行后直接 `DRAFT -> COMPLETED`。
- 计划保存生成新的 `PlanVersion`，不覆盖历史计划。
- 所有查询校验 `tenant-id` 和当前用户。
- 不新增合作方、归因和佣金字段。

**完成定义**

- 迁移脚本可在 fresh DB 执行。
- 创建、更新、列表、详情、邀请撤销和越权测试通过。
- API 返回的状态与 v1.2 完全一致。

### XJ-C1-02 用户身份、临时令牌与私人制品权限

**目标**

把当前成书 `@PermitAll + owner token` 收敛为可恢复但不泄露私人素材的权限模型。

**实现要求**

- 案例页匿名可看；上传原图前建立用户或受限临时账户；付款前绑定正式用户。
- 临时令牌只访问一个草稿，带过期、撤销、哈希存储和速率限制。
- 私人原图、精确位置、PDF、订单和地址不能仅凭可猜 URL 访问。
- 图片标签无法加认证头时使用短期签名 URL，不把长期 owner token 放查询参数。
- 保留 `tenant-id`，补充跨租户和横向越权测试。

**完成定义**

- 未登录、过期令牌、错误用户、错误租户和撤销令牌均失败关闭。
- 合法用户能从 H5 刷新页面后恢复自己的任务。
- 日志和错误响应不包含令牌、签名 URL、手机号和地址全量。

**目标**

- Worker 继续只做媒体生成，不直接修改订单状态。

- 保留现有 `/v1/jobs` 内部契约，外部 APP 只调用 `/app-api/xunjing/**`。

- 每任务使用非特权隔离工作区和只读原图，限制网络、文件、CPU、内存、磁盘、超时、并发和重试，不持有主库/支付/物流写凭据。

### XJ-C2-02 行后照片识别与实际旅程重建

**目标**

用户旅行结束后直接选择照片，无需预先建计划，也能生成可核对的 `ActualVisit`、时间线和 `MemoryEvent`。

**实现要求**

- 结合 EXIF 时间/GPS、视觉地点证据、照片相似性和用户补充。
- GPS 不是唯一依据；缺失时仍可按时间、视觉和用户目的地工作。
- 地图与“旅程时刻”双向联动；用户点击地图标记或时刻卡时，另一侧定位到同一照片簇。
- 实轨、照片地点顺序、交通衔接和未知断点分别输出，禁止为完整画面合成一条连续实线。
- 只提出最多 3 个会影响封面、章节、地点、人名或隐私的问题。
- 低置信度普通细节概括或省略，不编造事实。
- 计划存在时生成轻量计划/实际对齐，但不覆盖 `PlanVersion`。

**完成定义**

- 至少三趟 100 张以上真实旅行样本，其中一趟无轨迹、一趟无 GPS。
- 输出可追溯到素材证据，用户能纠正关键地点。
- 无照片、照片跨多趟旅行和时间错误有恢复路径。

### XJ-C2-03 旅行书真实首版、翻页与轻修改

**目标**

打通 `StoryProject -> BookVersion -> 保护性首版 -> RevisionRequest -> APPROVED -> PRINT_READY`。

**实现要求**

- 首版直接展示完整书，不先要求选模板或逐页编辑。
- 首版同时提供“整本节奏”总览，展示章节、页型、地图页和需确认问题，并能从缩略图跳到真实跨页。
- 拍摄时间与可靠位置驱动照片分组、章节和地图；位置不足时降级为地点卡、区域页或无地图章节，不能补画精确路线。
- 页型必须包含受控节奏规则；同构跨页默认不连续超过 2 个，叙事页默认不超过 6 张照片。
- 当前跨页只提供 2–3 个通过裁切、出血和文字安全检查的备选版式，不提供模板市场或空白画布。
- 使用成熟翻页组件或轻量自研适配，但移动端、键盘和降级阅读模式必须可用。
- 修改支持换封面、替换照片、隐藏地点/人物和 500 字内自然语言要求。
- 修改前给出影响页范围；每次生成新版本，可回退。
- 付款前预览低清或带保护标识；印刷版必须用原图重建。
- 自动检查页数、出血、DPI、字体、溢出、缺图、重复、地图和隐私。
- Harness 必须真实加载 `travel-memory-book` Skill，产出源素材 manifest、`journey-model.json`、编辑 brief、`selection-ledger.json`、`book-plan.json`、`visual-direction.json`、可编辑首版、全页预览、`revision-history.json`、印刷 PDF、制品 manifest 和 QA 报告或具有同等语义的类型化制品。
- 原图只读并保留 SHA-256；用户修订生成新 `BookVersion`，不原地覆盖已批准版本。

**完成定义**

- 100–250 张真实照片生成 40–60 页完整样书。
- 有 GPS、无 GPS 和元数据部分缺失的样本分别生成符合证据门槛的地图页或降级页面。
- 整本节奏总览、跳页、换版、问题确认和真实翻页均有手机视口操作证据。
- 首版、修改版、回退版和印刷 PDF 均有真实制品与哈希。
- 至少 80% 标准测试书无需运营逐页调整。

- 只访问公开允许、正式接口或用户授权的数据。
- 保存来源 URL、平台、获取时间、解析版本和失败原因。
- 提取地点、日期、交通、住宿、餐饮和注意事项；POI 歧义必须标记。
- 链接失败回退到正文、截图或手工地点，不绕过登录/验证码/反抓取。

**完成定义**

- 至少三种真实来源样本和三种失败样本。
- 获取失败不会卡死 Trip，也不会把未经核实信息标成实时事实。

### XJ-C3-02 路线核对与动态计划预演

**目标**

根据当前 `PlanVersion` 自动生成 15–30 秒计划预演和可交互逐日查看。

**实现要求**

- 地图镜头、交通方式、日期、地点和距离来自真实计划。
- P0 只做 2–3 套自动模板，不做专业时间轴编辑器。
- 路线修改后生成新预演版本，旧版本可追溯。
- 明确标记“旅行计划”，不能冒充真实走过的轨迹。
- 使用合规地图、来源和审图号。

**完成定义**

- 手机端 60 秒内完成可播放预演作为目标门槛；超时进入后台并可恢复。
- 修改地点顺序、交通方式和日期后，画面及字幕同步变化。

### XJ-C3-03 同行免安装查看与加入

**目标**

同行通过 H5/小程序卡片看懂计划，无需投票；获得邀请后可加入同一 Trip。

**实现要求**

- 区分 VIEWER 只看链接和 MEMBER 加入邀请。
- 邀请有有效期、可撤销、可见范围和使用次数。
- VIEWER 看不到原图、精确位置、订单和收货信息。
- 加入后才允许补充素材；创建者控制计划和最终成书。

**完成定义**

- 未安装 APP 的手机浏览器可查看。
- 过期、撤销、越权和重复接受邀请测试通过。

### XJ-C4-01 今日行程、导航调起和记下这里

**目标**

行中提供有用但不打扰的轻模式。

**实现要求**

- 主操作只有下一站、详情和导航；记录入口为次级。
- 调起合规第三方地图，不自研转向级导航。
- “记下这里”默认只保存时间和地点，照片、语音、心情均可选。
- 拒绝定位、未打开应用或未记录不影响行后成书。

**完成定义**

- 真机完成打开今日行程、调起导航、返回和记下这里。
- 权限拒绝、无地图 App、离线和计划变更有明确反馈。

### XJ-C4-02 同行共同素材与归属

**目标**

同行按需补充照片、视频、语音和备注，并保留贡献者和个人删除权。

**实现要求**

- 每条素材必须有 `contributorMemberId`。
- 成员只能删除自己的素材；OWNER 删除整趟旅行触发统一删除任务。
- 多人轨迹分别存储，不拼成伪造的单人轨迹。
- 不做复杂多人实时编辑和投票。

**完成定义**

- 两名真实测试账户完成加入、上传、撤回和成书归属检查。

### XJ-C5-01 旅行故事、足迹卡、完整回放与回忆电影

**目标**

从同一 `StoryProject` 生成可回看的实际旅程、可分享的故事、足迹卡和竖屏回忆电影。

**实现要求**

- 计划电影只用计划数据，回忆电影优先用实际地点和真实素材。
- 无完整轨迹仍可生成，不能用计划路径冒充实际路线。
- 完整旅程回放按整趟、日期和时刻分层；地图、路线进度、时刻卡、照片/视频和故事必须同步。
- 支持播放/暂停、前后时刻、拖动、按日/时刻跳转、0.5×/1×/2×速度和地图标记跳转。
- 回放中的实线、点线、虚线和断点语义必须与实际旅程和书中地图一致。
- P0 固定模板自动成片；只开放换封面、隐藏片段、长短/情绪调整。
- 公开制品带必要地图来源、生成标识和隐私模糊。

**完成定义**

- 同一 Trip 生成两类电影时来源和文案标识正确。
- 无轨迹样本可以完整回放地点与时刻，且不会出现伪造道路级连续线。
- 播放、拖动、日期跳转、地图标记跳转和回放结束入口有真实手机视口操作证据。
- 9:16 回忆电影可在目标手机播放和分享，视频/音频基本 QA 通过。

### XJ-C5-02 作品库与基础个人旅行档案

**目标**

用户按 Trip 找到路线、故事、电影、旅行书版本和订单，并从已完成作品形成基础个人足迹。

**实现要求**

- 列表来自服务端，不以 localStorage 作为事实源。
- 支持生成中、失败、待修改、已付款、印刷中、已签收和售后状态。
- 基础足迹只聚合已保存旅行，不要求用户补录全部历史。
- 默认不公开精确轨迹。

**完成定义**

- 跨设备登录能看到相同作品和订单。
- 删除、失败和处理中状态不会显示成已完成。

### XJ-C6-01 运营后台、异常处理与质量看板

**目标**

运营人员能处理真实异常，而不是逐单人工制作。

**实现要求**

- 查看 Trip、上传、重建、电影、成书、订单和履约状态。
- 自动质检失败、高风险内容、投诉和人工精修才进入例外队列。
- 支持重试、取消、退款、重印和删除任务，不允许直接篡改已完成历史。
- 看板展示上传成功率、生成成功率、人工介入、两轮定稿、印刷准时、重印、退款和单本贡献毛利。
- 看板展示 Runner 健康、队列/并发、Harness/SDK/模型/Skill/渲染器/QA 版本、`skillLoaded`、Skill SHA-256、分阶段耗时、token/成本、重试、QA 失败、灰度和回滚。

**完成定义**

- 每种异常至少一个真实或受控故障注入样本。
- 运营动作有权限、审计和前后状态证据。

## 5. 并行执行边界

最多建议三条并行泳道：

| 泳道 | 可执行任务 | 禁止重叠 |
| --- | --- | --- |
| A：业务底座 | C1-01、C1-02、C1-03、C1-04 | 同时修改相同 SQL、状态枚举、Controller |
| B：C 端体验 | C2-01、C3-01、C4-01 | 同时修改 `pages.json`、首页和共享请求层 |
| C：内容与制品 | C2-02、C2-03、C5-01 | 同时修改 Worker 核心渲染和制品 manifest |

订单履约 C2-04 必须等待 C2-03；作品库 C5-02 必须等待服务端事实源；C6-02 只能在所有 P0 任务完成后开始。

两项都必须是 `0 0`。
